# Rail: stop folding agents at 4 — show them all, scroll the rail

## The defect

`src/renderer/components/sidebar/ProjectRail.tsx:246` hard-codes:

```ts
const FOLD = 4
```

and at :304-305 a collapsed group renders `live.slice(0, FOLD)` with the remainder counted into a
`+N` button (:445-459). The cap is a **constant, not a measurement**. Observed live: a project with
five live agents shows `O C D Q` then `+1`, with the entire lower half of the rail empty. Nothing
was gained by hiding that agent — there was never a shortage of space.

The user's call, verbatim: *"there's plenty of space, the +1 could exist but should be clickable to
expand, i rather view all the agents, and the whole rail to scroll if needed."*

## Second defect, same control

The `+N` button's `onClick` is `onOpenProject(p.id)` and its tooltip reads *"N more agents — open the
project"*. It **looks like an expander and behaves like navigation** — clicking it switches the
active project instead of revealing the hidden agents. That is the two-verbs-one-glyph trap: a
control whose appearance promises one verb and whose action performs another. Whatever survives
here, `+N` must mean *show me those agents* and nothing else.

## What to build

1. **Show every live agent by default.** Delete the fixed `FOLD` cap. The scroller at :282-298
   already has `overflowY: 'auto'`, so a rail that genuinely overflows scrolls — that is the
   intended overflow behaviour, per the user.
2. **If you keep any fold at all, it must be space-derived, not a constant.** The existing comment
   justifies the cap as keeping neighbouring projects on screen; that rationale only holds when
   several groups actually compete for height. A cap may only engage when the rendered content
   would exceed the scroller's height — never when there is room. When in doubt, prefer the simple
   version: no cap, let it scroll.
3. **`+N` expands in place.** If a fold engages, its click toggles that group's expansion (per-
   project state), revealing the rest inside the rail. It must NOT call `onOpenProject`. Update the
   tooltip to match the verb it now performs. Provide the collapse affordance too if a group can be
   re-folded.

## Constraints

- Do not disturb the scroll-into-view effect at :250-263 — it measures `offsetTop` against the
  scroller and depends on that element staying `position: relative`. Verify a tall group still
  brings its own header into view rather than scrolling past it.
- `data-rail-fold` is not referenced by any test or selector (checked) — you may change or drop it,
  but if a fold survives, keep a stable hook on it.
- Both rail widths matter: collapsed (`RAIL_W`) and expanded (`RAIL_W_OPEN`). The fold is currently
  collapsed-only (`collapsed ? … : live`); whatever you do must be coherent at both widths.
- House style: no browser focus rings, no solid accent fills, colours via CSS vars only, and never
  recede the extra orbs with group `opacity`.

## Verify

- A project with 5+ live agents in a rail with free space shows **all** of them, no `+N`.
- Enough agents/projects to overflow: the rail scrolls, and no agent is unreachable.
- If a fold engages, clicking `+N` reveals the hidden agents **without changing the active project**.
- `npm test` green (603 tests as of `8d41a80`), `npm run build` clean.
