## ⚠ The renderer is being killed roughly hourly — measured, not theorised

A watcher (`/tmp/webcontent-watch.log`) captured peaks immediately before death:

```
20:57:05  RESPAWN  peak RSS before death: 1089MB
21:54:24  RESPAWN  peak RSS before death: 1196MB
```

**Caveat: the watcher used `pgrep … | head -1`, and pid 88147 "dies" then reappears — impossible.**
So it was flip-flopping between two WebContent processes and the rapid 20:23–20:24 cluster is
unreliable. The two above are credible (fresh monotonic pids, ~1h apart). **Fix the watcher before
trusting more of it: track every WebContent pid, not the first.**

This is upstream of at least three bugs already fixed downstream of it (routing loss, project
resurrection, reshuffle) — a respawn re-hydrates and each defect fires. The fixes make a respawn
*harmless*; they do not stop it. `sample` output from a live near-ceiling renderer is at
`/tmp/webcontent-watch.log.sample` if it fired.

**Load context:** 27 lanes running, renderer ~1.2GB. The dispatch-delivery race is documented as
load-dependent, so fewer concurrent lanes should reduce both the respawns and the stranded
dispatches.

## Traps worth not re-learning

- **`git add <dir>` in the main repo sweeps the user's untracked WIP into your commit.** Stage
  recovered files by explicit path.
- **Pre-copying a brief to a lane's directory does not work** — launching an idle lane creates a
  *new* worktree. Use an absolute path in the dispatch.
- **Read the durable state, not the UI.** el-encanto looked disconnected; `sessions.json` proved all
  six alive and correct.
