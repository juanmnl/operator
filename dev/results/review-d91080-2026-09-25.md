## Findings, most severe first

### 1. High — the Diff panel's exemption lets Merge drop a running lane's newest uncommitted work

- **Where:** `src/renderer/components/session/DiffPanel.tsx:45,62-80`; `electron/src/main/worktree.ts:721`.
- **What:** 465bbba exempts the panel's own lane (`exceptTerminalId`) from the live-lane refusal.
  `handleMerge` commits only when `hasChanges`. That value comes from the diff loaded when the panel
  mounted (`reload` runs once, in `useEffect`) and is not refreshed before merging. `mergeBranch` then
  merges the branch and calls `removeWorktree`, which renames the whole directory into the trash
  **with no status check on the worktree**. The lane's pty is killed only afterwards, in
  `onSessionEnded` (`DashboardView.tsx`, `handleSessionEnded`).
- **Failure scenario:**
  1. The user opens Review on a Code lane that is still working. The diff shows 2 files.
  2. The user commits them with the panel's Commit button. `hasChanges` is now false.
  3. The agent writes `src/foo.ts` and is mid-turn.
  4. The user presses Merge. There is no commit, because `hasChanges` is false. The merge contains only
     the earlier commit, and `removeWorktree` moves the directory, `src/foo.ts` included, into the trash.
  5. The background sweep deletes it.

  The same happens without step 2 if the agent writes after the panel loaded. The exemption covers
  exactly the lane that is most likely still writing.
- **Before this branch:** the same loss existed; there was no guard at all. 465bbba does not add it,
  but the exemption is the path the brief asked about, and it is not safe.
- **Fix:** kill the exempt lane's pty *before* the commit and merge, not after. And in `mergeBranch`,
  run `git status --porcelain` in the worktree after the merge and keep the worktree, don't remove it,
  if anything is uncommitted.
- **Discard:** `handleDiscard` (`:85`, button `:177`) has **no confirmation**, and with the exemption it
  deletes the running lane's worktree and `branch -D` in one click. That is the button's purpose, but a
  one-press, unrecoverable delete of an active lane's branch deserves a confirm naming the branch and
  "the lane is still running". Pre-existing.
- **Path matching:** the other half of the brief's question is clean. `liveLaneIn`
  (`worktree.ts:671`) uses the same `containsPath`/`realOf` as the reaper's `ptyClaimOn`. `realOf`
  resolves the deepest existing ancestor and re-appends the rest, so `/tmp` and `/private/tmp` match
  even for paths that no longer exist. `checkoutsOf` reads git's own `worktree list --porcelain`, and
  those resolved paths go through the same `realOf`. If git fails, it falls back to the named path
  only, which still refuses on the panel's own path.

### 2. Medium — "Remove N safe worktrees" now deletes any small non-git directory, called "leftover from an interrupted worktree creation"

- **Where:** `worktree-reap.ts:1350-1356` (new), classifier `:259`, label `:287`.
- **What:** Debris is any direct child of the worktree root that is git-invalid, has no provenance, is
  unregistered and is ≤ 2 MB (`DEBRIS_MAX_BYTES`, `:69`). Before this branch, `reap()` refused debris
  ("no source repo recorded"). Now it goes through `removePlainDirectory` from the one-press safe tier.
  The only checks left are the nested-`.git`-directory walk and `liveClaimNow`, which matches ptys by
  **spawn cwd** only.
- **Failure scenario:** A lane works in a directory it made itself under `~/.operator/worktrees`, as
  mantel lane t2 did about 40 times, per `dev/results/mantel-55da80-gutted-2026-09-25.md`. For example a
  plain `mkdir` scratch directory, or a self-made worktree that `gh … --delete-branch` half-removed. It
  holds 300 KB of notes or a patch. The lane's pty cwd is its original worktree, so nothing claims this
  directory. The directory is debris, so it is in the auto tier. The user presses "Remove N safe
  worktrees", and the row reads "Leftover from an interrupted worktree creation". The folder goes to
  the trash and is swept.
- **Fix:** keep debris out of the auto tier unless it matches the actual interrupted-creation shape.
  That shape is a directory with at most a stray file and a `.git` pointer to a missing admin entry
  (the `.tmpIBNq7t` case). Otherwise route debris through the Settings selection with the plain-path
  second confirmation, which is already mandatory for plain removals (`entryNeedsConfirm`).

### 3. Medium — dropping stale claims also drops the only protection for lanes of a second Operator instance

- **Where:** `worktree-reap.ts:758` `claimIsLive` and `:777`; boot wiring `index.ts:246`.
- **What:** A `sessions.json` claim now counts only if **this** process's pty table has a pty there.
  `sessions.json` lives in the shared `~/.operator`, so a second main process on the same `OPERATOR_DIR`
  does not know the first one's ptys and treats every live lane as unclaimed. An example is a dev build
  launched without an isolated `OPERATOR_DIR`; the project memory makes isolation a rule precisely
  because it has happened.
- **Failure scenario:** the packaged app runs a Code lane in `operator-abc123`, merged-clean, or dirty
  only with copies (G2). A dev instance started without `OPERATOR_DIR`:
  - offers it in Settings with no "a lane is open here" and, now, no second confirmation;
  - puts it in the safe tier if it is merged-clean;
  - at its boot, runs `drainPending(false)` for real on the packaged app's pending records.

  Any of these moves the live lane's cwd into the trash.
- **Fix:** keep the file claim when it was written by another live app pid. `sessions.json`, or the
  lease file, can carry `appPid`. `leases.ts` already tracks `appPid` for this reason. Drop only claims
  whose writer is dead.

### 4. Medium (latent) — quit still drains *every* pending record, and boot now queues one for every lane open at the last quit

- **Where:** `reapOnQuit` `:1447` calls `drainPending(!AUTO_REAP_ON_TRIGGERS)` with the default
  `which` (all records). `queueEndedSessions` `:1397` now queues any record whose claim no pty backs.
  At boot, that is **every** lane that was open at the last quit, because no pty exists yet.
- **Failure scenario:** someone flips `AUTO_REAP_ON_TRIGGERS` to true, as the comment at `:53` invites

  launch. The next launch's restore offer then shows them "folder missing", which is the exact harm the
  `userStartedRemoval` comment (`:1270-1277`) says ended-session records must never cause.
- **Today:** nothing happens while the flag is false.
- **Fix:** pass `userStartedRemoval` at quit as well, and correct the `:53` comment.

### 5. Low (fails safe) — G3's boot retry misses most lanes, because `queueRemoval` keeps the first record for a path

- **Where:** `worktree-reap.ts:1257`.
- **What:** Boot queues an ended-session record for each lane open at the last quit (see 4). When that
  lane is later closed, `removeWorktreeDurably` → `queueRemoval(… 'lane close')` is a no-op, because a
  record for the path exists. If that close is interrupted, the surviving record still says "ended
  session", so boot skips it.
- **Result:** for any lane that lived across a restart, the interrupted-close retry never happens. Safe
  direction (nothing is deleted), but G3 only works for lanes created in the same run.
- **Fix:** let a user-started reason replace an ended-session record.

### 6. Low — the `BRANCH_SAFETY_NOTE` leaves the coordinator guessing

- **Where:** `src/renderer/lib/roster.ts:416`.
- **What:** "If another lane *may* have it checked out, merge without `--delete-branch`". But every
  worktree lane always has its own branch checked out in its worktree, so any PR from a live worktree
  lane, not only the `checkout -b` case, gets its lane's worktree removed by `--delete-branch`.
- **Failure scenario:** a coordinator decides a Code lane "is done" and merges its PR with
  `--delete-branch` while the lane is still open. The lane's cwd disappears. The new watcher reports it,
  but the checkout is already gone.
- **Fix:** make it a rule, not a judgement. Check `git worktree list` for the branch, or never use
  `--delete-branch`; delete the remote branch only.
- **Also:** the note reaches only lanes spawned after this lands. Running coordinators keep the old note
  until restarted.

### 7. Low — Rescue marks a folder "preserved" while skipping directory entries (dirty submodules)

- **Where:** `worktree-reap.ts:1165-1176` (`else continue` at `:1174`), `:1202`.
- **What:** Rescue copies status entries that are files or symlinks and silently skips directories. The
  fingerprint then matches, so the folder counts as preserved, and removal needs no second confirmation.
- **Failure scenario:** a worktree with a submodule that has uncommitted edits. Status shows ` M sub`,
  `lstat` sees a directory, and the entry is skipped. `changes.patch` records only
  `Subproject commit …-dirty`. After Rescue, "Remove" goes through without the unsaved step, and the
  submodule's edits are gone.
- **Nested repositories:** they appear as `?? dir/` and are also skipped. They are caught later by
  `removeWorktree`'s nested-`.git` walk, but submodules have a `.git` *file*, which that walk ignores
  (Review L6, still open).
- **Fix:** if any status entry is a directory, return `preserved: false`, and say which entry.
- **Minor:** two rescues at once can overwrite `index.json` (last write wins). Safe direction.

### 8. Low — the "Merged by squash or rebase" label replaces the class label

- **Where:** `WorktreesSection.tsx:642`.
- **What:** `mergedByPatch` is computed for any row whose branch is not an ancestor, including
  `live-claimed`, `unattributed` and `corrupt`. The label then replaces "A lane is open here", "No
  provenance record" or "Not a valid git worktree".
- **Failure scenario:** a lane whose PR was squash-merged while it keeps running. Its row reads "Merged
  by squash or rebase". The checkbox is still disabled, but the reason is hidden.
- **Fix:** append the patch-merged note to the class label instead of replacing it.

### 9. Low — pty batching adds up to 16 ms to every keystroke echo

- **Where:** `pty-batch.ts:59`.
- **What:** The timer is trailing-edge only. An isolated read, such as a typed character's echo or
  Claude's composer redraw, waits the full `FLUSH_MS` before it is sent. The comment says "the renderer
  cannot show output sooner than its next paint anyway". That holds for a read that arrives mid-frame,
  but here a read is delayed a full frame whenever it arrives right after a paint.
- **Fix:** flush immediately when the buffer is empty and no flush happened in the last `FLUSH_MS`
  (leading edge), and batch only while reads keep coming.
- **Not measured in the GUI.**

### 10. Nit — the checkout-gone tooltip may overclaim

- **What:** It says "Files not committed there are gone". If gh uses a non-`--force`

  clean tree. Whether gh passes `--force` is not verified. Consider "may be gone".

## Areas checked and clean

**Pty batching** (`pty-batch.ts`, `terminals.ts`):
- Bytes are concatenated in arrival order and never split or re-encoded. `Buffer.from(chunk, 'utf8')`
  is unchanged from before, and node-pty's `StringDecoder` keeps characters whole, so batch boundaries
  are character-aligned for the renderer's streaming `TextDecoder`.
- `onExit` calls `close()` (flush) before `this.onExit`, so no output trails the exit event.
- `kill()` flushes before signalling. Reads during the grace period are flushed by `close()` when the
  exit arrives.
- After `close()`, reads pass straight through. The timer is cleared on every flush, so none survives
  an exited terminal. A timer that fires after `kill()` deleted the map entry only sends to a dead id,
  which is harmless.
- Size cap: a flush at ≥ 64 KB, reads ≤ ~1 KB, so a message is at most about 65 KB.
- History is now fed from the flush, so `terminalHistory` never includes bytes still waiting to be sent
  live.
- The `outputFor(() => managed)` getter is only called at flush time, so there is no TDZ problem.
- The [subscribe, snapshot] duplicate from the scrollback report (D6) is unchanged, neither better nor worse.

**Scrollback freeze fix** (`terminal-options.ts`, `resyncViewport`), checked against xterm 6.0.0 source:
- `scrollToLine(viewportY, true)` sets `_latestYDisp` and an absolute position. `_handleScroll` sees
  diff 0. `queueSync()` with no argument then resets `scrollHeight` and clamps, and skips
  `setScrollPosition` because `ydisp === _latestYDisp`.
- It runs on both deactivation and activation, which covers ended lanes that are never reactivated.
- `applyPaneActivation` is the only place that sets `scrollback` (`git grep`).
- The pin to exactly 6.0.0, and the canary in `terminal-activation.test.ts` that fails if
  `_core._viewport.queueSync`/`scrollToLine` disappear, are sound.

**`dirtIsNonWork`** (`worktree-reap.ts`, G2):
- Only `??` entries are ever excused. Any tracked change returns false up front.
- `sameBytes` requires both sides to be regular files (`lstat`) with equal size and equal bytes.
- The default-branch path compares `hash-object --no-filters` ids against `ls-tree` blob ids. A
  pathspec glob can only fail to match, never falsely match, because the map is keyed by the exact path.
- A nested repository (`?? dir/`) makes `hash-object` fail, which counts as work.
- There is a cap of 5000 entries.
- A missing or unknown source repo returns false.
- The tests cover unique files, copies at a different path, tracked edits, non-root symlinks and a
  missing source. Missing: a same-size, different-content file. The code handles it (full byte
  compare), but the test would pin it.

**`liveClaims` in main and the boot wiring** (`index.ts:246`):
- `setLivePtyCwds` is wired before `reconcileAtBoot` reads any claim. At boot the table is truly empty,
  because main owns every pty and none survive a restart.
- The `--mcp-serve` process leaves it unwired and still trusts the file.
- Deferred-launch ptys count as live (`!exited`).
- The only gap found is the cross-instance case (3).

**`drainPending(false, userStartedRemoval)` at boot:**
- It acts only on user-started records.
- It holds anything live (pty), anything unreadable, and anything with uncommitted files or commits on
  no other branch. A lane close WIP-commits first, so its own-branch commits keep it held.
- It still goes through `removeWorktree`'s guard, vouch and nested checks.
- A record whose path could be reused cannot be, because `reattachWorktree` refuses an existing path.

**Settings `removeSelected`:** unchanged gating. Plain-path removals still always need the second
confirmation.

**Charter migration and prune** (`roster.ts`, `prune-seeded-lanes.ts`):
- Verified by script: main's `DEFAULT_ROLE_PROMPTS` for code, review, design and qa are each found
  verbatim in `legacyStockCharters`.
- `migrateStockCharters` replaces them and leaves a customised prompt untouched. It is idempotent, and
  it composes with `clearSeededRoleFields` (at worst one extra hydrate to settle).
- The Infra preset's id does not collide with existing preset ids. `routeDispatch` still matches real
  lanes before presets.

**Checkout watcher** (`checkout-health.ts`):
- A missing `.git` only raises the alarm for a known worktree (seen healthy, or a direct child of the
  worktree root). A main checkout (`.git` directory) is never flagged.
- It forgets on exit, and the sweep drops non-live lanes.
- It is throttled to one probe per lane per 20 s.
- The renderer re-reads the list after a reload without re-announcing it.
- It is read-only by design.

**Trash log and stray files:** the log is bounded (256 KB, drops the older half) and never throws.
Stray files are listed only.

**#1 in detail**

- After the merge, `mergeBranch` re-reads `git status --porcelain` in the worktree. It keeps the

**#3 in detail**

**#9 in detail**
- The leading-edge send happens only when nothing is buffered and no timer is pending. It therefore
  cannot overtake earlier bytes.
- Reads within `FLUSH_MS` of the last send are batched as before. `lastSentAt` is set inside `flush()`

- `close()` and `kill` still flush, and after `close()` every read goes straight through.
- Mixed traces I walked by hand:
  - quiet read, burst, quiet, burst;
  - a size-cap flush followed by a read within 16 ms (batched, not quiet);
  - a timer flush followed by a read at +9 ms (batched).

  Each keeps order and loses nothing.
- A backward clock jump makes `now - lastSentAt` negative, so reads just batch; a forward jump sends
  early. Both are safe.
