## The main question: can a terminal end up never fitted, or fitted to a stale size?

**No stuck hold found.** Every path that sets `layoutMove` also clears it:
- `beginLayoutMove` (`DashboardView.tsx:356`) always calls `restartLayoutSettle` (`:346`). That starts a
  300 ms timer, then sets `pinW: null`, then clears `layoutMove` after two animation frames.
- A new toggle cancels both the timer and the frame id currently stored. The outer frame hands
  `layoutSettleRaf` to the inner one, so the cancel always reaches the live one. Rapid repeated toggles
  therefore just push the settle out and end in one clear.
- Unmount clears both (`useEffect` cleanup).
- Lifting the hold goes through `TerminalPane`'s existing `useEffect(() => { if (!suspendFit)
  handleResize() }, [suspendFit])`, which always fits the active pane. The fit is quiet-gated and
  bounded by `FIT_MAX_DEFER_MS`.
- Timeouts can be delayed while the window is hidden, and the frames do not run until it is shown
  again, so the settle can come late. It always comes, and it fits when it does.

The two-step settle is sound. Step 1 releases the pin while `suspendFit` is still on, so every
ResizeObserver callback returns early (`shouldFitOnResize`). Step 2, two frames later, lifts
`suspendFit`, and the active pane fits once at the settled width.

Other cases checked:
- **Window resize during a move:** `windowResizing` is a separate term in `suspendFit` (`:5446`). The
  final fit happens after both clear. The pin is released at settle whatever it was.
- **Reduced motion:** `beginLayoutMove` returns early (`:359`), so there is no hold and no pin. The rail
  transition is `none` (`layoutTransition`), and the slot does not animate. The pane fits once from its
  ResizeObserver, as on main.
- **Reversal mid-move:** `pinWidth(prev, live, delta)` keeps the maximum of the running pin, the live
  width and the target. A reversal returns to the first move's start, which the first pin already
  covered. That holds even if `toggleSidebar`'s `sidebarCollapsed` closure is a render stale.

The findings below are transient wrong sizes, not permanent ones.

## Findings, most severe first

### 1. Medium-low — a lane switch or launch during a move still lands a fit at the pinned width, and the slot animates it anyway

- **Where:** `DashboardView.tsx:5405` (pin), `:5622` (`animate={!!layoutMove?.panel}`);
  `SidePanelSlot.tsx:21-24` (the contract); activation fit on main `terminal-options.ts:219`.
- **What:** `layoutMove` stays set for the whole 300 ms window regardless of what happens in it. Two
  paths bypass `suspendFit`:
  - **Activation.** `applyPaneActivation` calls `hooks.fit()` directly in its write callback. A lane or
    project switch inside the window fits the incoming pane to the stack's current width, which is
    `pinW`. For a narrowing move (opening the panel, expanding the rail) that is the **wider start
    width**. The pty is resized to the wide column count. Claude Code redraws at that width, and the
    right edge of the TUI is clipped by the card. At settle the pane refits to the real width: a second
    SIGWINCH and a second redraw. In classic TUI mode the first redraw can stay in scrollback wrapped at
    the wrong width.
  - **A lane mounted in the window.** Examples are a dispatch creating a lane, or a restore. The
    deferred launch starts `claude` at the pinned width (`ensureInitialFit` fits directly), so the
    startup banner is composed for a width the pane will not have.
  - **The slot contract is broken.** `SidePanelSlot` says a lane switch "stays instant … a slot still
    moving underneath it would make that fit land at a mid-move width". But `animate` reads the sticky
    `layoutMove.panel`, so a lane switch that flips `panelOpen` inside the window **does** animate, and
    its activation fit lands mid-move, which is exactly what the comment rules out.
- **Failure scenario:** press ⌘B to expand the rail and press ⌘2 to switch lanes within 300 ms. Or
  Operator auto-creates a lane from a dispatch just as you open the panel. The incoming lane renders one
  frame-to-300 ms at the wrong column count, then refits.
- **Compared with main:** main had the same exposure during `sidebarAnimating`, and no hold at all for
  the panel, so this is not a regression. But the change's own contract claims more than it delivers.
- **Fix:** end the move on a lane or session switch: `setLayoutMove(null)` and clear the timers when
  `activeTerminalId`/`activeSessionId` changes. Alternatively, have the activation path skip its direct
  fit while `suspendFit` is on and leave it to the settle fit.

### 2. Low — a slow panel mount can outrun the settle timer, releasing the hold before the slide plays

- **Where:** `DashboardView.tsx:346-364` with `SidePanelSlot.tsx:74-83`.
- **What:** the settle timer starts at the toggle (`LAYOUT_MOVE_MS + 40` = 300 ms). The slide starts two
  frames after the mount, and then `onMoveStart` restarts the timer. If the mount is long enough that
  the first timer fires and its two frames run before `onMoveStart`, `layoutMove` is already `null`.
  `restartLayoutSettle` cannot bring it back, because it only edits a non-null move. The slide then plays
  with no hold and no pin: per-frame ResizeObserver fits, and `animate` has already been read as true.
  The mount is measured at about 150 ms in the harness; a heavy Preview or Plan plus a busy renderer
  could pass about 270 ms.
- **Failure scenario:** opening the panel on the Preview tab while several lanes stream. The terminal
  refits on several frames of the slide (quiet-gated), which is the multi-resize this change removes.
- **Fix:** for a panel open, don't arm the settle timer until `onMoveStart`, or have
  `onMoveStart` re-assert `layoutMove` if it has been cleared.

### 3. Low (existing, not introduced) — narrow windows and gallery entry

- **Narrow windows.** `panelW` has no upper bound against the window ("No upper bound on load", around
  `:303`). A width stored in a wide window, reopened at 1000 px with the rail expanded, can push the card
  below 50 px. `doFit` then returns early (`offsetWidth < 50`) and the terminal is never fitted to that
  size: it keeps its previous columns, which with the pin is the wide start width. Design's result file
  names the 244 px / 29-column case at 460 px. This is the same code path on main.
- **Gallery entry.** Entering a session from the gallery expands the rail without `beginLayoutMove`, so
  that animation has no hold. Also acknowledged in the result file.

### 4. Nit — a stale `sessionLayouts` closure can start a no-op move

`setPanelOpen` (`:367`) decides `cur !== open` from the `sessionLayouts` in its closure. A call made
before the previous patch has rendered can start a move that changes nothing: 300 ms of held fits and
one refit. Harmless.

## Areas checked and clean

- **The pty never resizes while hidden.** `shouldFitOnResize(active, suspendFit)` is unchanged. The pin
  resizes every pane's container, but inactive panes return early and catch up on activation. The
  scratch shell (`ShellSheet`) now takes `suspendFit` too, so it no longer refits every frame of ⌘B.
- **Timers and listeners:**
  - `layoutMoveTimer` and `layoutSettleRaf` are cleared on restart and on unmount.
  - `SidePanelSlot` cancels its frame in the effect cleanup and its `Animation` on unmount. `onfinish` is
    guarded by `animRef.current !== anim`, and a cancelled animation does not fire it.
  - `useReducedMotion` removes its `matchMedia` listener. It was moved out of `StatusWave` unchanged.
  - The rail adds no listeners.
- **SidePanelSlot:**
  - A reversal reads the live width, so a close during the paused two-frame window measures 0 and
    unmounts at once.
  - A drag resize while open does not restart the move, because `full` is read, not a dependency.
  - Closing with `animate` false unmounts in the layout effect.
  - The Preview kept in the panel while it slides out (`preview={effPanelTab === 'preview' && mainView
    !== 'preview' …}`) cannot mount twice: the main view's Preview is exclusive with it. `renderPreview`
    is pure JSX, so calling it while the slot is unmounted is harmless.
- **Conflict with `operator/d91080`'s scrollback resync:**
  - The merge is textually clean, and typecheck and both suites pass on the merged tree.
  - They do not interfere. `resyncViewport` runs in `applyPaneActivation` on an `active` change and
    reacts to `scrollback` changes, while this branch changes widths and `suspendFit` and never touches
    `scrollback`. A fit resizes xterm through `onResize`, which already re-syncs the viewport.
  - d91080's 16 ms output batching does not change the fit's quiet gate (`FIT_QUIET_MS` = 150 ms).
- **The Preview's native inspect view** is hidden for the duration of a move (`inspectHidden … ||
  !!layoutMove`) and re-placed afterwards. No stale placement.

## Recommendation

Mergeable, and it merges cleanly with d91080. Fix 1 before or right after: end the move on a lane or
session switch. That makes the `SidePanelSlot` contract true and removes the one path to a fit at the
pinned width. Fix 2 is a one-line guard. Items 3 and 4 can wait.

## Final pre-merge check (031e7bb), 2026-09-25

**Finding 1 (move leaks into a lane switch) is fixed.**
- A move now belongs to the session and terminal it started on (`moveFor`, `layout-motion.ts:74`). The
  render that activates another lane reads `activeMove = null` (`DashboardView.tsx:372`), so it has no
  pin, no `suspendFit` and no slot animation.
- An effect then drops the move and its timers (`:412`).
- A running slot animation is finished on the spot (`SidePanelSlot.tsx:64`). The rail's transition is
  set to `none` (`:5137`), which ends a running transition at its end value.
- The incoming pane's activation fit runs in a passive effect, after those layout effects, so it
  lands at the settled width.
- Residual, Low: a lane launched **in the background** (for example by a dispatch) during a move does
  not become active, so the move is not ended. Its `ensureInitialFit` then starts Claude at the pinned
  width until its first activation refits it. It is rare, and it corrects itself on activation.

**Finding 2 (slow mount) is fixed.** An opening panel arms a 1500 ms fallback, and the real settle
starts from `onMoveStart` (`:145`).

**The yield rule, `placePanel`, has no loops or oscillation** (`session-layout.ts:163`).
- It is a pure function of the window width, the rail state, the stored panel width, the tab's minimum
  and a constant console minimum (`:328`). Nothing it outputs feeds back into its inputs; the terminal's
  measured width is never read. So a placement cannot cause another placement.
- Its mode changes only when the window width, the rail, the tab (Preview's larger minimum) or the
  stored width change. There is no hysteresis. Dragging the window across the boundary flips dock and
  overlay per resize event, but fits are held by `windowResizing` for the whole drag and happen once
  when it settles.
- A mode change is never animated (`canAnimate` requires the same mode), so the terminal fits once
  from its ResizeObserver.
- The overlay drawer takes no width, so opening or closing it never refits the terminal.
- Nits:
  - In dock-narrower mode, dragging the handle wider stores a larger width that is not drawn until the
    window has room.
  - A drag inside the 300 ms after a toggle animates per frame.
  - `terminalCellWidth()` is measured once and cached. A system font not yet available at first call
    would fix a fallback metric for the session (SF Mono is a system font, so this is unlikely).
