## 1. `--mcp-config` shape, dev + packaged — PASS

The flag isn't built by `buildArgs` itself (that function only handles session/permission/model
args) — it's `TerminalManager.buildCommand` in `electron/src/main/terminals.ts:168` that does:

```ts

```

`mcpConfigArg` (`src/renderer/lib/launch-args.ts`) is the pure builder. Ran its 11-test suite
(`launch-args.test.ts`, all pass) and independently called it myself for both shapes:

```

dev:      {"mcpServers":{"operator":{"command":"/repo/node_modules/.bin/electron","args":["/repo/electron","--mcp-serve"]}}}
```

`command` is `process.execPath` in both; `--mcp-serve` is always the last arg; dev additionally
prepends `app.getAppPath()` so Electron doesn't open an empty shell. Matches the claim exactly.
(The `buildCommand`-level wiring — the `app.isPackaged` branch itself — has no dedicated
integration test; see "Not unit-tested" below.)

## 5. Hop accounting — ring test, fast + slow — PASS

`src/renderer/lib/agent-delivery.test.ts`, `'the loop test — two lanes answering each other MUST
terminate'` → `'stops even when the pair brake cannot help — a ring of many lanes'`:

```
$ npx vitest run src/renderer/lib/agent-delivery.test.ts
✓ 35 tests passed
```

Both ring variants terminate as designed:
- **fast** (1s apart, pair repeats every 8 steps) → blocked with `reason: 'pair-brake'`
- **slow** (spaced ≥ `PAIR_WINDOW_MS` apart, no pair ever repeats in-window) → blocked with
  `reason: 'hop-limit'` and a note containing `"no human in the loop"` — this is `LANE_SEND_LIMIT`
  (24) firing, reported under the same `BlockReason` enum value as an ordinary hop-count block but
  distinguished by its note text (`BlockReason` only has 4 members: `paused | hop-limit |
  pair-brake | queued` — no separate `lane-limit` reason exists, and that's intentional, not a
  mislabel).
- `slow.delivered <= LANE_SEND_LIMIT * ring.length` (8 lanes × 24 = 192 ceiling) — asserted and
  holds.

Both variants hit their 2000-iteration ceiling with room to spare; neither runs away.
